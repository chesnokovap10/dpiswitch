How DPI Switch works

All traffic of the computer goes through the AmneziaWG tunnel by default. Alongside, a detector checks, site by site, whether your ISP interferes with the direct path. A site that works direct, and is not slower there, is switched to a direct connection and remembered: it opens faster and sees your real ISP. Everything else stays in the tunnel.

The detector only ever takes sites out of the tunnel, one at a time, after checking them. When in doubt a site stays in the tunnel: a wrong "clean" breaks a site, a wrong "blocked" only costs a detour.

Every list takes sites (example.com, +.example.com for the domain and all under it), addresses and networks (1.2.3.4, 192.168.0.0/16) and programs (telegram.exe, or a full path for one copy) in any mix. A name in its own letters (госуслуги.рф) is written as the core sees it, in punycode. An address counts for connections made to it by address: a browser reaches sites by name, so add a site by its name. The tries the Forbidden list refuses show on a tab of their own in Live.

How a site is checked

  1. The detector watches the connections the core carries and picks up the names in them (the name is read from the connection itself, so programs with their own DNS count too).
  2. The name is resolved through the DNS for direct sites: the node that traffic would really go to.
  3. That same node is contacted twice: directly and through the tunnel. On each path: TCP connection, TLS handshake with the name in it (SNI) and a full certificate check, an HTTP request and its answer. A name seen on UDP 443 is also tried over QUIC (HTTP/3). The ports the name was really used on are the ones probed.
  4. This is repeated several times (attempts per probe). The name is clean only if every attempt is clean, and the direct path is not slower than the tunnel by more than the tolerance.

Checks run every 10 seconds, up to 20 names at a time, 8 at once. The checks pause while the tunnel fails the core's own health checks, and for a cycle after sleep or a network change: the measurements would say more about that moment than about the path.

On the Verdicts page a click on a column's head sorts the table by it, a second one the other way; by name by default. The sort is kept in the browser.

Terms and re-checks

  • A clean site goes direct for the term set (7 days by default), then it is checked again. If the check cannot confirm it, it goes through the tunnel until the next one.
  • A site found slower once is not reverted at once: it is measured again after the re-check interval, and only a second "slower" in a row sends it back to the tunnel.
  • A blocked site is tried again after the re-check interval (1 hour by default). Each check in a row that finds the same doubles the wait, up to the pause cap (1 day).
  • Names are re-checked only while something still goes to them. One nothing has used for a day is left alone, and after ten days it is forgotten. If its term is over, the Verdicts page says "when next used" for it.

Whole domains

When a domain has 3 or more clean subdomains and none blocked, slower or failing directly, the whole domain (+.example.com) goes direct: new subdomains do not wait for a check. The first bad subdomain removes the rule. It helps services with pools of servers: CDNs, speed tests, updates.

DPI bypass: cutting the ClientHello

ISPs block many sites by name: they read it off the first message of a TLS connection (the ClientHello) and cut the connection. With the cut on, a site found BLOCKED_TLS is checked once more -- through the core's direct-split outbound, which cuts the ClientHello into two TLS records in the middle of the name and sends them as two TCP segments, the boundary between them inside the first record. The DPI does not find the name, and the server puts the message together as usual: TLS allows it to be split into records. The check is as strict as a plain one: the same node, the handshake, a request and its answer, and the speed against the tunnel.

  • It passes: the verdict is CLEAN_SPLIT, and the site goes direct with the cut, for the same term as a clean one. Its QUIC (UDP 443) goes as the QUIC decoy says, below.
  • It fails: BLOCKED_DPI ("DPI bypass failed"), and the tunnel. It is re-checked on the same schedule as other blocks, with the cut each time. Only slower than the tunnel: SLOWER.
  • Only the first message is cut; the rest of the traffic goes as it is. Encryption is not touched: the browser checks the certificate itself.
  • Every network keeps its own verdicts: measured on 03.10.2026, one ISP let the cut through almost everywhere, a mobile one only to some addresses (Google's yes, Meta's and Akamai's no).
  • It can break traffic: the check opens the main page, and other parts of the site, or the ISP's later rules, may not take the cut. A connection left open with no answer has the site checked again before its term. So it is off by default.
  • Switched on, it checks the BLOCKED_TLS names again at once. Switched off, it takes them off the direct path at once and closes their connections: they open again through the tunnel.
  • It works in On and Observe only. In On only the names checked go with the cut. In Observe only with the cut on everything goes with it at once, before any check: a name not checked would hang until the detector got to it. The names the detector found clean without the cut go direct as they are. In Tunnel only nothing goes direct, the cut included; the detector checks and records there too.
  • {{if .St.Second}}With no first tunnel{{else}}With no tunnel{{end}} (awg1 not loaded) there is nothing to compare against, and the detector checks the cut alone: a site is tried direct as it is, and when it is cut on its ClientHello, direct with the cut. CLEAN_SPLIT only when the cut gets a certificate that passes the chain check and an answer; speed is not compared. Once awg1 is loaded, such verdicts are the first checked again against it.
  • Such names make no family (Whole domains): the domain is blocked by name.

DPI bypass: the QUIC decoy

QUIC (UDP 443) carries the name in its first packet, the Initial, and the ISP cuts it by that name just the same. With the QUIC decoy on (the default), QUIC to the sites going direct with the cut goes direct too: ahead of a connection's first packet the core sends a decoy one with the name www.google.com, the ISP judges the connection by it and lets the real one through.

  • The detector checks QUIC this way too: QUIC blocked direct is tried again with the decoy. Where it does not help, QUIC to the site is refused ("QUIC refused" in the verdicts), and the browser takes TCP at once.
  • A site clean over TCP with only its QUIC blocked goes direct with the decoy rather than to the tunnel. One whose QUIC gets through with the decoy while its TCP is blocked even with the cut goes direct over QUIC, its TCP on 443 refused.
  • Switched off, QUIC to every site going direct with the cut is refused, and the browser takes TCP; the names that go direct over QUIC alone go back to the tunnel. Its open QUIC connections close and open again the new way.
  • It works only together with the ClientHello cut: only the cut's names take that way. In Observe only with the cut on, all QUIC goes with the decoy; with the decoy off, QUIC goes direct as it is.
  • Switching it needs no core restart.

Auto-switch: on, observe only, tunnel only

The detector checks sites and records verdicts in all three modes; the modes differ only in where the traffic goes.

  • On: the verdicts are applied. Unblocked sites go direct, the rest by the lists and through awg1.

  • Observe only: plain direct -- a whitelist. Everything goes direct but the lists, which go their way as in every mode. The second tunnel starts switched off each time this mode is chosen: switch it on on its page, and its presets and list go to awg2 too. The detector checks everything that goes direct.
  • Tunnel only: a strict mode. Everything but "Always direct" goes through the tunnels and never direct: with the tunnels down it fails. "Always direct" is the one way out past the tunnels.

The second tunnel's switch is kept per mode: switched off in On, it is off again whenever On is chosen, and so for Tunnel only. Switched off, its presets and list route nothing.

    Networks

    Verdicts are kept per ISP (its AS number): another network of the same ISP shares them, another ISP starts its own. Without a network the checks pause and the memory is kept. On the Verdicts page the network in the header opens the list of the networks kept: the one picked has its verdicts shown, and the page's reset and ✕ act on it alone. Leaving the page goes back to the current network. The tray's reset is of the current network.

    DNS

    • Direct sites are resolved by the resolvers for direct sites, asked outside the tunnel: CDNs then answer with nodes near your ISP. The detector uses the same resolvers, so it tests the node the traffic will go to. DoH or DoT by address is the safe choice: many ISPs block or tamper with plain DNS.
      • {{if .St.Second}}
    • Tunnelled sites are resolved inside the tunnel they go through, by that tunnel's own DNS: awg1's and awg2's are set apart, each from its .conf unless set. A .conf with no DNS = and nothing set: the names are resolved by the resolvers for direct sites, outside the tunnel.
      • {{else}}
    • Tunnelled sites are resolved inside the tunnel, by its own DNS: the one set here, or with none set the one from its .conf. A .conf with no DNS = and nothing set: the names are resolved by the resolvers for direct sites, outside the tunnel.
      • {{end}}
    • Programs get stand-in addresses from the core (198.18.0.0/16, 2001:2::/48) and the core resolves the real one on the chosen route. That is why a name, not an address, decides the route.
    • Local DNS cache (off by default): the core asks the service for direct sites' names, not the servers. A name it knows is answered at once from memory, with no server asked; an answer is kept for 7 days from when it was last fetched and outlives restarts of the core and of Windows, and one past its TTL is given at once and fetched again behind it. A new name is asked of the fastest resolver for direct sites, the others joining in when it is slow. Answers are kept per network, and the detector asks the same cache. Resolvers given by name, not by address, are not asked by the cache.

    IPv6

    With IPv6 on, the computer gets IPv6 even where the ISP has none: it goes through the tunnel. Where the ISP has IPv6 of its own, sites going direct -- plain or with the DPI bypass -- use it too, and the detector checks a site's IPv6 address beside its IPv4 one: the worse of the two is the site's verdict, so a site cut on IPv6 alone does not go direct. If the tunnel's server has no working IPv6, the program finds out and resolves IPv4 only for it: the core restarts once, and that finding holds for a day before it is checked again.

    With IPv6 off there is none at all, the ISP's own included: programs get no IPv6 addresses for names, and a connection made to an IPv6 address is refused at once, so the program takes IPv4. Nothing leaves over IPv6 around the tunnel. The local network's own addresses -- the router's, a printer's -- work as before.

    UDP leak guard

    A program that binds its UDP socket to the Wi-Fi or Ethernet adapter's own address leaves by that adapter whatever the routes say: around the tunnel, with your real address in the packet. A browser's WebRTC does it to show a site who you are; so do the calls of Discord and Telegram, games and torrent clients. UDP leak guard (off by default) blocks every UDP packet out of a cable, Wi-Fi or mobile adapter that is not the core's own, while the core runs and its adapter takes the traffic. What goes into the DPI Switch adapter is not touched, nor is the local network -- private, link-local and multicast addresses: the router, a TV you cast to, printers, devices' discovery -- or DHCP.

    It is put into the Windows Filtering Platform, the layer Windows Firewall and third-party firewalls are built on, not into Windows Firewall's rules: it holds with the firewall off or another one in charge. All it needs is the Base Filtering Engine service; with that stopped the settings page says so and nothing is blocked. Once the filters are in, the service sends a test packet out of each adapter by its own address and reads the engine's record of the packets it dropped: if it has them all, the page says it was checked.

    It can break what needs UDP out of the adapter itself: another VPN's (WireGuard, OpenVPN, IKEv2), a call or a game that binds to the adapter and has no other way. A device on the local network with a public address is cut off. The filters live in the service's own session: they go out when the core stops or restarts, when the setting is switched off, and with the service should it die.

    The second tunnel

    Second tunnel in the settings switches it on and off altogether (off by default). Off, it is not connected to its server, and its page and whatever the others say of it are gone; its config, presets and list are kept. With its config loaded, switching it restarts the core: connections drop for a couple of seconds. The Use the second tunnel switch on its page does not restart the core.

    A second AmneziaWG server for chosen services only: YouTube, Telegram and WhatsApp, Discord, AI services, social networks and your own list. It stands below Forbidden, Always via tunnel and Always direct and above the detector, which leaves its names alone. If it is down, its sites go through the first tunnel; if both are down, direct -- in Tunnel only refused. The detector measures the direct path against the first tunnel only: what goes to awg2 is never checked, and without awg1 nothing is, even with auto-switch On. Until it is attached, its presets and list route nothing. Use the second tunnel on its page switches it off and on: switched off, its presets and list route nothing, and what they name goes the way the other lists and the mode send it.

A change applies at once, like a switch. Once a built-in preset is deleted or edited, Restore built-in presets… puts them back as the program ships them; your own presets stay.

    When a site does not open

    1. Look it up on the Verdicts page with the filter. If it goes direct and should not, add it to Always via tunnel (+.example.com for the whole domain). A right-click on its row sends it to a list straight away, as on Live; the ✕ in the row resets that one verdict: the site goes through the tunnel until the detector checks it again. Rows are picked as on Live: Ctrl and Shift pick several, and the right-click and ✕ on a row picked act on all the rows picked at once.
    2. If many sites broke at once (a new block by the ISP), reset all verdicts: everything goes through the tunnel and the detector starts over.
    3. If a site must see your real address (a bank, government services), add it to Always direct.
    4. The logs show every verdict with its reason.
    5. The Live page shows which route its connections take right now, and by which rule; a right-click on a row sends the site straight to the list it belongs in.

    Live

    The connections the core holds, refreshed every second: the program, the host, the address, the port, the type, the route, the speed and the bytes both ways. A row's colour is its route: green direct, {{if .St.Second}}blue the first tunnel, violet the second, grey the detector's checks;{{else}}blue the tunnel, grey the detector's checks;{{end}} closed rows have none. Hover over a route for the group and the rule that chose it.

    • Tabs. Open, Closed, Failed, Forbidden — the tries the Forbidden list refused — and All. Beside them, a filter by route, a search by host, program and address, and "Hide the detector's checks". A click on a column's head sorts the table by it; the columns keep their widths.
    • Time is when it happened: an open connection's, when it opened; a closed one's, when it closed; a failure's, its last try. Not today, the date goes under it. How long a connection lasted is in its hint.
    • States. open; open, but no traffic for over 30 seconds; closed; failed: the core could not make the connection.
    • Type. TLS, QUIC and HTTP are told by the port: the likely protocol, not one seen, with a dashed badge. Where the core read the site's name from the traffic itself the protocol is confirmed, and the badge is solid.
    • Failures are only written to the core's log, and the program reads it all the time. In place of the speed and the bytes a failed row says why: timed out, refused, reset, name not found, no network interface, closed by the other side; the tooltip has the error in full. The same program failing again to reach the same address by the same route and rule, for the same reason, is no new row but "×N" on the old one. A failure's route is its group's choice at the time: with the tunnel down and the group gone direct, it shows as direct. The detector's checks fail too, as they should on a blocked path.
    • History. The core keeps no closed connections: the program asks it every second from the tray's start, whether the page is open or not, and sees one leave. The closed ones and the failures are kept for the core's whole run, however old: the last 100,000 of each. When the core starts anew the history starts over: the service names every run of the core, so a restart shows even between two calls. The history lives in the tray's memory and is gathered anew when the tray restarts. A connection that opened and closed within a second may never show.
    • Pause stops the table, not the gathering: what closes and fails meanwhile is there when you resume. A page in the background takes nothing, and coming back takes only what it missed.
    • While the cursor is over the rows they keep their order: new connections and a new sort wait until it leaves the table, so the row pressed is the row pointed at; the numbers go on changing.
    • A row clicked is picked and holds its place: sorted by speed, the others move around it, and a connection that closes stays where it was, closed. A click anywhere else, or a change of tab, filter or sort, lets it go. Ctrl+click adds a row to the ones picked or takes it away, Shift+click picks the rows from the one clicked before to this one, Ctrl+Shift+click adds them to the ones picked; all the rows picked hold their places. A plain click on a row picked keeps them all picked: only a click on another row, or outside the table, lets them go. ✕ in a row closes the connection in the core: the program reconnects, and the new connection follows the rules as they are now. ✕ on a row picked closes the connections of all the rows picked.
    • A row right-clicked opens a menu. On top, what to send: the whole domain (+.example.com), the name alone, the address (a list routes by address only the connections made to it by address) or the program. {{if .St.Second}}Then where: Direct, Via the tunnel, Via the second tunnel (its own list), To a preset (the presets switched off are greyed: they route nothing), Forbid.{{else}}Then where: Direct, Via the tunnel, Forbid.{{end}} File location opens the program's folder with its file picked out — for the detector's checks, DPI Switch's own; greyed for several rows picked and on the Verdicts page. On a row picked the menu is for all the rows picked: on top, in place of one name, groups with their count (Whole domains, Names only, IP addresses, Programs, the lines themselves in the tooltip), and the group picked goes to the list in one action.

    A line sent from the menu goes to the list chosen, and the open connections it moves are moved at once. For it to take that route, the menu takes it out of wherever a rule would route it first. The core's rules come in this order:

    1. Forbidden;
    2. Always via tunnel;
    3. Always direct;
      4. {{if .St.Second}}
    4. the second tunnel: its presets switched on, then its own list;
      5. {{else}}{{end}}
    5. the detector's verdicts.

    A list whose rules come before the one chosen loses every line routing it, a wider one too: +.example.com for api.example.com, 10.0.0.0/8 for an address in it, a program by its name for a copy of it by its path. A wider line goes whole — a list cannot hold an exception for one name — so the answer names what went, and from where. A list whose rules come after it loses the same line and the narrower ones only: a wider line there is in nobody's way. {{if .St.Second}}The presets stand below every list: a line sent to a list leaves them as they are, and a line sent to a preset is taken out of the lists. The lists and the presets change as one:{{else}}The lists change as one:{{end}} a file failing to write puts back the ones written before it.

    Files

    Everything is kept in {{.St.DataDir}}: the configs (locked to administrators and you, they hold private keys), the lists, the settings, the verdicts (controller-state.json), every probe (reports.jsonl) and the logs.

    The program itself is installed in {{.St.InstallDir}}: the service and the tray run from there. Only administrators can change that file — the service runs as SYSTEM.
